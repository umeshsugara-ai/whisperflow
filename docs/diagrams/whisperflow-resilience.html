② Case 1 — Hotkey press → mic open (the "flicker" chain, now fixed)

PortAudio's WASAPI backend only accepts the device's native mix rate (48 kHz) — our 16 kHz request needs auto_convert. Without it every pinned-mic start failed (-9997), fell back slowly, and the user's release landed as an instant stop: a 0.00s "flicker".
RECORD_START → resolved device → stream open (with both failure exits)
solid blue — default flow
solid pink — conditional branch
solid green — success terminal
dashed amber — retry / try again
Shipped fixes on this path: uses_wasapi() probe + auto_convert (commit 6827899) kills the -9997; WASAPI-row preference in resolve_device (8c6d846) dodges the DirectSound row that dies with -9999 after sleep/lock; the retry + "Mic busy" pill mean the worst case is one visible message, not a dead hotkey.

③ Case 2 — Sleep/resume silently kills the keyboard hook

Windows destroys WH_KEYBOARD_LL hooks across sleep, and the `keyboard` library latches listening=True forever — the app looks alive but never sees another key. An in-process watchdog probes the hook with a raw injected F24 and rebuilds it when the probe vanishes.
Hook liveness probe → rearm loop (wf-hook-watchdog thread)
solid blue — default flow
solid pink — conditional branch
solid green — success terminal
dashed amber — loop back / re-check
Hard-won details: the keyboard lib's own press_and_release('f24') silently never reaches the hook (broken scan-code map for high F-keys, verified live) — the probe must use raw ctypes SendInput. UIPI: when an elevated window has focus the probe is blocked too; rearm churns harmlessly (WARN once, then debug).

④ Case 3 — App crashes: sibling watchdog relaunches it

A watcher inside the app dies with the app. WhisperFlowWatchdog.exe is a separate 1.7MB stdlib-only process that waits on the app's process handle — it survives anything that kills the app, including native faults and Task Manager.
Process exit → exit-code triage → report + relaunch (with crash-loop guard)
solid blue — default flow
solid pink — conditional branch
solid green — success terminal
dashed amber — resume watching loop
dashed cyan — sibling process spawn
Two subtle rules: armed only after a fully successful startup (a config that dies at launch must NOT be relaunch-looped), and exit code None (handle already gone) never relaunches — don't guess next to a possibly-running instance.

⑤ Case 4 — App frozen: heartbeat staleness catches what exit codes can't

A hung app never exits, so the crash path never fires — the live 27-Jul incident: process alive 7+ hours, UI half-dead. The app now proves liveness by touching a file from the Tk mainloop itself; the sibling watchdog treats staleness as a crash.
Heartbeat tick (app) ∥ staleness poll (watchdog) → terminate + relaunch
solid blue — default flow
solid pink — conditional branch
solid green — success terminal
dashed amber — periodic loop
Why root.after and not a thread: a background thread would keep beating while the UI is frozen — scheduling the write on the mainloop makes the heartbeat die exactly when the thing we care about dies. Missing heartbeat ≠ stale: only a beat that existed and then aged out counts (old builds and fresh launches can never false-positive).

⑥ Case 5 — Wrong/virtual default mic (the Camo trap)

Fresh installs follow the Windows default mic — and Windows silently makes virtual devices like "Microphone (Camo)" the default. Everything "works" except the audio is pure silence. This burned real teammates before the picker shipped.
Silent-mic detection → in-app mic picker → pinned device
solid blue — default flow
solid pink — detection firing
solid green — success terminal
dashed amber — try another device
Why pinning matters: "default" re-resolves on every recording — Windows can flip it to Camo at any time. A pinned name is immune to that, and (post-⑥ fix) the pinned name resolves to its WASAPI row with auto_convert, dodging both DirectSound death and the 16 kHz rejection.

⑦ Case 6 — Clean quit & installer upgrade: recovery must NOT fire

A self-healing system is only trustworthy if it also knows when to do nothing. Two intentional-exit paths are explicitly distinguished from crashes.
Intentional exits — watchdog stands down
solid blue — default flow
solid green — by-design terminal
The kill-order rule: killed second, the watchdog would read the app's forced exit as a crash and relaunch it in the middle of the install. Same rule applies to manual debugging: an intentional Stop-Process on WhisperFlow.exe gets auto-relaunched — kill the watchdog first.
